# The sm120 node: RTX 5090 in a Kubernetes server

The lab's latency tier: a consumer RTX 5090 (32 GB) in a home-lab server
that runs a real Kubernetes stack — the point being that "local AI" here
means production plumbing, not a demo notebook.

## The box

- **RTX 5090**, 32 GB GDDR7 — roughly 7× the memory bandwidth of the
  GB10, one quarter of the memory. Hence the opposite optimization order
  ([framing](../README.md#the-framing)): quality → **memory** → speed.
- Runs as a node in a small Kubernetes cluster (Talos Linux, GitOps via
  Flux — every serving config is a commit, rollbacks are `git revert`).
- **Power lesson:** the 5090's millisecond load transients can trip a
  PSU's over-current protection — presenting as hard machine crashes that
  look exactly like driver failures. They weren't. A 570 W power cap on
  the GPU has kept it stable since, at negligible throughput cost.

## Serving

Same custom vLLM sm12x line and the same 27B NVFP4 quant as the GB10 —
one quantization stack, two opposite configs:

- **NVFP4 KV cache** is what makes a 27B with long context fit in 32 GB
  at all: ~469k tokens of KV headroom, ~4× what fp8 KV would allow.
- **~72 tok/s** single-stream decode — the interactive tier.
- Speculative decoding stays off for now: the one drafter that proved
  clean (DFlash2) currently forces fp8 KV, the wrong trade on a
  memory-bound box
  ([`notes/dflash2-sm121-first-light.md`](../notes/dflash2-sm121-first-light.md)).

## The two-tier architecture

A LiteLLM gateway in front of both nodes makes them one endpoint:

1. Interactive sessions land on the 5090 (fast tokens).
2. The gateway counts active sessions; above the cap, new sessions are
   routed to the GB10 ([`nodes/dgx-spark-gb10.md`](dgx-spark-gb10.md))
   with a notice injected so the agent knows it is on the slower tier.
3. Session slots expire on a TTL — a stuck counter once took the whole
   gateway down, which is why the counter is time-bounded now.

Latency where it matters, capacity where it's cheap, one API for every
client.

## What it actually does

Interactive agent sessions — the harnesses people actually type into.
Multi-agent and batch work overflows to the GB10; long-context jobs
belong there outright (a length-based routing rule is on the list).
